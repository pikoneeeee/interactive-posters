# Интерактивные Плакаты — Продукт и Система Активации

## 1. Описание продукта

**Интерактивные Плакаты** — цифровой образовательный продукт для школ Казахстана. Приложение отображает мультиязычные (KZ/RU/EN) интерактивные учебные плакаты по школьным предметам.

### Платформы
| Платформа | Формат | Где используется |
|-----------|--------|-----------------|
| **Windows** | `.exe` (PyInstaller) | Школьные компьютеры → вывод на большой экран/проектор |
| **Android** | `.apk` (WebView) | Интерактивные доски с Android OS |

### Предметы (12 шт.)
Физика, Математика, Биология, Химия, География, Информатика, История Казахстана, Всемирная история, Казахский язык, Русский язык, Английский язык.

### Технический стек
- **Windows**: PySide6 + QWebEngineView, сборка через PyInstaller
- **Android**: Kotlin + WebView, сборка через Gradle (product flavors per subject)
- **Контент**: HTML/CSS/JS плакаты (~100-160 на предмет), Tailwind CSS, Chart.js
- **Шрифты**: Inter, Montserrat (локальные .woff2)

### Как доставляется продукт
1. Сборка EXE/APK с нужным предметом (один предмет = одна сборка)
2. Запись на USB-флешку
3. Установка на устройство заказчика
4. Заказчик вводит ключ активации
5. Продукт работает

### Особенности бизнес-модели
- **Продажа поштучно**: один заказчик покупает один предмет (или несколько отдельно)
- **Один ключ = один предмет на одном устройстве**
- **Офлайн-установка**: интернет на устройстве НЕ гарантирован
- **Код и контент обновляются постоянно** — новые плакаты, исправления, новые предметы
- **Продажи идут по ходу** — ключи нужно генерировать быстро и гибко

## 2. Текущая система активации (проблемы)

### Что есть сейчас (`licensing.py`)
```
Формат ключа: ПРЕДМЕТ-ТИП-ГОД-ЧАСТЬ1-ЧАСТЬ2
Пример:       PHYSICS-EDU-2026-ABCD-1234
```

- Ключ проверяется локально по формату (5 частей, год не истёк)
- При активации сохраняется `license.dat` с хешем ключа + device_id + subject
- `device_id` = SHA256 от UUID материнской платы (Windows) / machine-id (Linux)
- Проверка: файл существует + device_id совпадает

### Проблемы текущей реализации

| # | Проблема | Последствие |
|---|----------|------------|
| 1 | **Нет криптографической защиты** | Любой может угадать формат и сгенерировать валидный ключ |
| 2 | **Нет привязки ключа к конкретному клиенту** | Ключ можно передать другому |
| 3 | **Нет учёта выданных ключей** | Не знаем кто что купил, сколько активаций |
| 4 | **Нет механизма отзыва** | Нельзя деактивировать утёкший ключ |
| 5 | **`license.dat` — plain text** | Легко подделать вручную |
| 6 | **Нет поддержки Android** | На Android другой способ получения device_id |
| 7 | **Нет обновлений** | Для обновления контента нужно переустанавливать |
| 8 | **Год в ключе — единственная "защита"** | Слишком просто обойти |

## 3. Лучшие мировые практики лицензирования офлайн-продуктов

### 3.1. Криптографические ключи (подход JetBrains, Sublime Text)
**Суть**: Ключ — это подписанный токен. Приложение содержит публичный ключ и проверяет подпись. Сгенерировать валидный ключ без приватного ключа невозможно.

- ✅ Работает полностью офлайн
- ✅ Невозможно подделать без приватного ключа
- ✅ Можно закодировать метаданные (предмет, срок, клиент)
- ❌ Нельзя отозвать без обновления приложения

### 3.2. Онлайн-активация с офлайн-работой (подход Microsoft, Adobe)
**Суть**: Ключ проверяется на сервере один раз. Сервер записывает device_id. Дальше работает офлайн.

- ✅ Полный контроль: кто, когда, на чём активировал
- ✅ Можно ограничить число активаций
- ✅ Можно отозвать ключ
- ❌ Нужен интернет хотя бы один раз
- ❌ Нужен сервер

### 3.3. Hardware-bound лицензионные файлы (подход MATLAB, AutoCAD)
**Суть**: Клиент присылает fingerprint устройства → вы генерируете подписанный файл лицензии → клиент кладёт файл на устройство.

- ✅ Максимальная защита
- ✅ Полностью офлайн
- ❌ Двухшаговый процесс (неудобно)
- ❌ При смене железа нужно перегенерировать

### 3.4. Периодическая онлайн-валидация (подход SaaS, Netflix)
**Суть**: Приложение периодически «звонит домой» для подтверждения лицензии.

- ✅ Максимальный контроль
- ❌ Требует постоянного интернета — **не подходит для школ**

## 4. Рекомендуемая архитектура

### Подход: **Криптографические офлайн-ключи + опциональный сервер**

Это гибрид подходов 3.1 и 3.2, оптимальный для наших условий.

```
┌─────────────────────────────────────────────────────┐
│                    ГЕНЕРАЦИЯ КЛЮЧЕЙ                  │
│                                                      │
│  Админ-панель (CLI / Telegram-бот / Web)            │
│  ┌─────────────┐    ┌──────────────────────────┐    │
│  │ Приватный    │───▶│ Подписанный ключ          │    │
│  │ ключ (RSA)  │    │ SUBJ-XXXX-XXXX-XXXX-SIG  │    │
│  └─────────────┘    └──────────────────────────┘    │
│         │                       │                    │
│         │              Записывается в БД             │
│         ▼              (клиент, дата, предмет)       │
│  Хранится только                                     │
│  у разработчика                                      │
└─────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────┐
│                 АКТИВАЦИЯ НА УСТРОЙСТВЕ              │
│                                                      │
│  1. Пользователь вводит ключ                        │
│  2. Приложение проверяет подпись (публичный ключ)    │
│  3. Из ключа извлекает: предмет, срок, ID клиента   │
│  4. Привязка к device_id (hardware fingerprint)      │
│  5. Сохраняет зашифрованный license.dat             │
│                                                      │
│  Опционально (если есть интернет):                  │
│  6. Отправляет на сервер: ключ + device_id          │
│  7. Сервер подтверждает / отклоняет                 │
└─────────────────────────────────────────────────────┘
```

### 4.1. Формат ключа

```
XXXX-XXXX-XXXX-XXXX-XXXX
```
25 символов (без дефисов), Base32 кодировка. Внутри закодировано:

| Поле | Бит | Описание |
|------|-----|----------|
| `subject_id` | 4 бита | Индекс предмета (0-15) |
| `client_id` | 16 бит | Уникальный номер клиента (0-65535) |
| `year` | 6 бит | Год истечения (2024+offset, до 2087) |
| `month` | 4 бита | Месяц истечения |
| `flags` | 4 бита | Тип лицензии, мульти-устройство и т.д. |
| `signature` | 96 бит | HMAC-SHA256 усечённый до 96 бит |

**Итого**: 130 бит → 26 символов Base32 → 5 групп по 5 символов + дефисы

### 4.2. Генерация ключей (приватная сторона)

```python
# keygen.py — ТОЛЬКО на вашем компьютере, НЕ в сборке
import hmac, hashlib, struct, base64

SECRET_KEY = b"ваш-секретный-ключ-256-бит"  # хранить в .env

SUBJECTS = {
    'physics': 0, 'mathematics': 1, 'biology': 2, 'chemistry': 3,
    'geography': 4, 'informatics': 5, 'historykaz': 6, 'worldhistory': 7,
    'kazakhlang': 8, 'russianlang': 9, 'englishlang': 10,
}

def generate_key(subject: str, client_id: int, year: int, month: int, flags: int = 0) -> str:
    """Генерирует подписанный лицензионный ключ."""
    subj_idx = SUBJECTS[subject]
    # Упаковываем данные (4 байта)
    payload = struct.pack('>I',
        (subj_idx << 28) | (client_id << 12) | ((year - 2024) << 6) | (month << 2) | (flags & 0x3)
    )
    # Подпись
    sig = hmac.new(SECRET_KEY, payload, hashlib.sha256).digest()[:12]  # 96 бит
    # Кодируем
    raw = payload + sig  # 16 байт
    encoded = base64.b32encode(raw).decode().rstrip('=')
    # Форматируем: XXXXX-XXXXX-XXXXX-XXXXX-XXXXX
    return '-'.join(encoded[i:i+5] for i in range(0, 25, 5))
```

### 4.3. Валидация ключей (в приложении)

```python
# licensing.py — встроен в сборку
import hmac, hashlib, struct, base64

# Публичный? Нет — HMAC использует shared secret.
# Но ключ обфусцирован в бинарнике PyInstaller / Kotlin.
_K = bytes([...])  # обфусцированный SECRET_KEY

def validate_key(key: str) -> tuple[bool, dict]:
    """Проверяет ключ. Возвращает (valid, {subject, client_id, year, month})."""
    clean = key.replace('-', '').upper()
    if len(clean) != 25:
        return False, {}
    # Добавляем padding для base32
    padded = clean + '=' * ((8 - len(clean) % 8) % 8)
    try:
        raw = base64.b32decode(padded)
    except Exception:
        return False, {}
    if len(raw) != 16:
        return False, {}
    payload, sig = raw[:4], raw[4:]
    # Проверяем подпись
    expected_sig = hmac.new(_K, payload, hashlib.sha256).digest()[:12]
    if not hmac.compare_digest(sig, expected_sig):
        return False, {}
    # Декодируем
    val = struct.unpack('>I', payload)[0]
    return True, {
        'subject': val >> 28,
        'client_id': (val >> 12) & 0xFFFF,
        'year': 2024 + ((val >> 6) & 0x3F),
        'month': (val >> 2) & 0xF,
        'flags': val & 0x3,
    }
```

### 4.4. Device fingerprint (кросс-платформенный)

| Платформа | Источник ID | Метод |
|-----------|-------------|-------|
| **Windows** | UUID материнской платы | `wmic csproduct get uuid` |
| **Android** | `Settings.Secure.ANDROID_ID` | Уникален для каждой установки |
| **Linux** | `/var/lib/dbus/machine-id` | Стабилен между перезагрузками |

Fingerprint = `SHA256(platform + raw_id)[:16]` — 16 hex-символов.

### 4.5. Хранение лицензии на устройстве

Файл `license.dat` — **зашифрованный** (AES-128-GCM или Fernet):

```json
{
  "key_hash": "sha256-хеш-ключа",
  "device_id": "A1B2C3D4E5F67890",
  "subject": "informatics",
  "client_id": 42,
  "activated_at": "2026-05-12T15:00:00",
  "expires": "2027-05-01",
  "app_version": "1.2.0"
}
```

Шифруется ключом, производным от device_id + встроенного salt. Подделать на другом устройстве невозможно.

```bash

# Результат: HF7KQ-ABCDE-XYZ12-MNOPQ-RST78
```

```
/newkey informatics 42 2027-05
→ 🔑 Ключ: HF7KQ-ABCDE-XYZ12-MNOPQ-RST78
→ 📋 Клиент #42, Информатика, до 05/2027
```
- Можно генерировать прямо с телефона

- Можно запросить список активаций

## 6. Обновление контента

### Текущая проблема
Плакаты обновляются часто, но для обновления нужно пересобрать EXE/APK и снова устанавливать через флешку.

### Рекомендация: дельта-обновления через USB
1. Скрипт `make_update.py` создаёт ZIP с изменёнными файлами + manifest
2. ZIP записывается на флешку
3. Приложение при старте проверяет флешку на наличие обновлений
4. Если найдено — применяет патч (копирует файлы в `content/`)
5. Лицензия и активация НЕ затрагиваются

## 8. Безопасность: что защищает, что нет

| Угроза | Защита | Уровень |
|--------|--------|---------|
| Угадать ключ | HMAC-подпись (96 бит) — 2⁹⁶ вариантов | ✅ Надёжно |
| Скопировать license.dat на другой ПК | Привязка к device_id | ✅ Надёжно |
| Подделать license.dat | Шифрование AES | ✅ Надёжно |
| Реверс-инжиниринг (извлечь SECRET_KEY) | Обфускация в бинарнике | ⚠️ Средне |
| Виртуальная машина с клонированным ID | Не защищено | ❌ Не критично для школ |

Для образовательного B2B-продукта этого уровня защиты более чем достаточно. Основные клиенты — школы, а не хакеры.
